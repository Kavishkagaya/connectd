# Decisions

One entry per deep dive. Newest last.

## #3 Repo layout — decided

Two repos.
- `openconnect` (OSS): everything a user needs. Kernel, drivers, runtime, SDK, CLI, providers, self-host dashboard. One monorepo; providers stay a package.
- `openconnect-cloud` (private): the managed layer. Multi-tenancy, user-code isolation, billing/metering, managed-only dashboard features.

## #4 License — decided

`openconnect` is Apache-2.0 (permissive, patent grant, best for adoption). `openconnect-cloud` is proprietary. Future versions may move to FSL if hosted competitors become a real threat.

## #6 Driver interface — decided

The driver provides infrastructure guarantees only, per instance. Everything an auth flow needs (handshake, credential record, single-flight, rate, outbox, config) is kernel code built on top.

Driver: `packages/kernel/src/driver.ts`
- `store`: `get` / `put` (optional TTL) / `cas` (versioned compare-and-swap) / `take` (atomic read+delete) / `delete`
- `timer`: durable named timers, `set` replaces, `cancel`; fired via `Handler.onTimer`
- `call(instance, method, args)`: cross-instance call; args/results are serialized
- `now()`: the clock (fake in tests)

Kernel → driver: `Handler { onCall, onTimer }`. Every event reaches an instance through it.

- **Async API.** Postgres can't be sync; semantic ops keep the DO fast anyway.
- **No full serialization guarantee.** Each store op is atomic, but handlers may interleave at awaits, as in Durable Objects. Races go through `cas`/`take`. The in-memory driver doesn't serialize either, so tests see the same races.
- **Cross-instance is hidden by the driver.** An app-scope rate instance is just another instance key.

Defaults for open points (held up through L1, #7–#11):
- OAuth callback routing: `state` = signed `connId.random`, no global lookup.
- Lifecycle state lives inside the credential record, so one `cas` covers both.
- Connection index by external id (#26) stays out of the driver until L3.

Validation: in-memory driver + DO driver must pass one shared parity suite (#13, #14).

## #13 Durable Object driver — decided

`@openconnect/kernel/do` (`packages/kernel/src/drivers/do.ts`): `durableObject(program, { binding })` returns a DO class. No separate package; a subpath export keeps `cloudflare:workers` out of anything that doesn't import it. Split only when a driver brings heavy deps (e.g. `pg`).

- One DO per instance key, created with `idFromName`; the key comes from `ctx.id.name`.
- SQLite storage: `kv(key, v, value, expires_at)`, `timers(name, at, payload)`, `seq(n)`. Every store op is synchronous SQL with no await inside, so it is atomic against other events.
- Versions come from one per-DO counter, so they never repeat after a delete (no ABA on `cas`).
- Expiry: filtered on read; expired rows swept on each write so abandoned handshakes don't pile up.
- Timers multiplexed on the single alarm, always set to the earliest timer. On alarm, fire due timers earliest first.
- `call` = RPC to `env[binding]` by `idFromName(instance)`, into the DO's `onCall`.
- No v1 migration (starting over, no production data). D1 as a global index waits for L3 (#26).

## #14 In-memory driver + parity — decided

- Fake clock: `now` is a plain number; `advance(ms)` moves it, then fires due timers.
- Timer semantics (both drivers): removed before firing (at-most-once; retries are the kernel's job, #11). `now()` during `onTimer` is the time it fired, not the scheduled time. A throwing timer is logged and doesn't block later ones. Timers set while firing run in the same advance if due.
- `@openconnect/kernel/parity`: one runner-agnostic suite (`parity(name, world, { test, expect })`) driven through a `probe` program. Memory runs it under `bun test`, the DO driver under `@cloudflare/vitest-plugin` in workerd, with a fake clock far in the future so real alarms never fire on their own.

## #7 Connection lifecycle — decided

`packages/kernel/src/primitives/connection.ts`. One `record` key holds state, sealed credential and an event outbox, so one `cas` covers all three.

- States: `pending`, `active`, `reauth_required`, `revoked`. "Refreshing" is in-memory single-flight, not a state. "Expired" is derived from `expiresAt`. Transient errors don't change state.
- Legal: none → pending | active. pending → pending | active | revoked. active → active | reauth_required | revoked. reauth_required → reauth_required | active | revoked. revoked is terminal (reconnect = new connection). `active` requires a credential.
- Triggers: `activate` (callback / re-auth), `revoke`, refresh `invalid_grant`, refresh retries exhausted, expired with no refresh token.
- Events: `{ seq, at, from, to, reason? }` on every state change, appended to an outbox inside the record (same `cas`). L3 reads `events.pending()` and calls `events.ack(seq)` (#24). Capped at 100; oldest dropped.
- Re-auth: the connection moves to `reauth_required` and keeps its id; a new handshake ends in `activate` on the same instance.
- Handshake: flow data under a TTL key; `state` = HMAC-signed `[instance, id]`, so `routeState` finds the instance with no lookup. `take` is single-use.

## #8 Token primitives — decided

- Credential is a tagged union: `oauth2` (`accessToken`, `refreshToken?`, `expiresAt?`, `raw` = full token response, which keeps extras like `instance_url` / `id_token`) or `static` (`fields`: API keys, basic auth, anything that doesn't refresh).
- Refresh is injected (`opts.refresh`); L2 wires it to `refreshGrant`. Single-flight per instance.
- Scheduling: timer `kernel.refresh` at `expiresAt - lead`, lead = min(5 min, half the lifetime), plus up to 10% jitter. `token()` also refreshes on demand inside 60s of expiry, and hands out the old token if a refresh fails transiently while it is still valid.
- Failures: `invalid_grant` → `reauth_required`. Anything else retries with backoff (30s base, 8 attempts) → `reauth_required` (`refresh_failed`).
- Rotation: the old refresh token is kept if the response has none. A lost `cas` after a refresh retries the write unless the credential was replaced meanwhile, so a rotated token is never dropped.
- Timer and `cas` aren't atomic; a crash between them leaves no timer, and `token()` covers it.

## #9 Rate primitives — decided

`packages/kernel/src/primitives/rate.ts`.

- GCRA: one number per key (TAT), exact, cheap. Burst = `count`, then one per `periodMs / count`. Keys expire once TAT passes.
- Scope = `{ instance, key, limit }`. Any scope (connection, app, workspace, custom) is just an instance key; remote ones go through `d.call(instance, RATE)`, so a Program routes `RATE` to `handleRate`. How a definition declares scopes is L2 (#17).
- Multi-scope `acquire` is in order and all or nothing: on a deny, earlier grants are refunded. `refund` for requests that never reached the provider.
- Provider headers via `observe`: `Retry-After` and `remaining: 0` + reset block until then; `remaining > 0` caps the burst. Only ever tightens.
- Reject with `retryAfterMs`, no queue: waiting is the caller's choice (L3).
- Deferred: cross-tenant fairness on a shared scope; sharding a scope hotter than one instance (~1k rps).

## #10 Secrets primitive — decided

`packages/kernel/src/primitives/secrets.ts`. v1 AES-GCM with a key-version byte, HMAC sign/verify, `importKeys` from env strings.

- `secrets(d, keys)`: sealed values in the instance store. Connector client secrets live in a per-app instance (replaces TeamDO); which instance is L3.
- Rotation: add the new version, make it current. Reads re-seal anything under an older key (both `secrets` and the connection credential). Retire the old key once nothing sealed under it remains.

## #11 Schedule primitive — decided

`packages/kernel/src/primitives/schedule.ts`.

- Multiplexing is the driver's job (done in #13 / #14).
- `retry(d, name, attempt, data, backoff)`: exponential with equal jitter (never 0), the attempt count rides in the payload so it survives restarts, false once attempts run out.
- No cron: recurring work re-arms its own timer from `onTimer`.

## #18 OAuth atoms — decided

`packages/kernel/src/primitives/oauth.ts`. Lives in the kernel (L1 per the roadmap), not in L2.

- Auth code + PKCE (`pkce`, `authorizeUrl`, `exchangeCode`), `refreshGrant`, `clientCredentials`, device code (`deviceAuthorize`, `devicePoll`; pending / slow_down come back as `OAuthError` codes), DCR (`register`), revocation (`revoke`).
- Client auth `post` (default) or `basic`; `clientSecret` optional for public clients. `fetchFn` passed in.
- Errors: `OAuthError(code, status, body)`, including 200-with-error (GitHub).
- do-connect's `src/oauth.ts` wasn't available locally; per-provider quirks come with #19 / #20.

## #17 defineConnection API — decided

`packages/connections` (`@openconnect/connections`). Held up through #19 with the small changes listed there.

- **Shape:** `defineConnection({ id, auth, metadata?, rate? })` is an identity function for inference. `auth` is steps, not a flow type: `start(ctx, input)` returns `{ redirect(state), data }` or `{ credential }` (done inline), then `callback(ctx, params, data)`, `refresh(ctx, cred)` and `revoke(ctx, cred)`, both optional. `ctx` = `{ config, fetch, redirectUri, now }`.
- **Helpers build the steps:** `oauth2(spec)` (auth code + PKCE by default) and `apiKey(fields)`. A custom flow writes the steps itself; the kernel still owns state, handshake, refresh scheduling and the outbox.
- **`bind(def, d, instance, opts)`** runs a definition on one instance over `connection()`: `connect`, `callback`, `token`, `metadata`, `revoke`, `onTimer`. #22 wraps it in the DO and HTTP routing.
- **Typing:** `C` = connector config (from the auth helper, e.g. `oauth2<{ clientId; clientSecret }>`), `M` = metadata (inferred from `metadata`'s return, must be `Json`). No schema library; config is validated where it's entered (L3/L4).
- **Metadata:** `metadata(ctx, cred)` runs *before* activation, so it doubles as the credential check (a bad API key never activates). Stored in its own `meta` key, not inside the record's `cas`: it's derived, and re-auth rewrites it.
- **Quirks:** config when they're data (`scopes`, `scopeSeparator`, `params`, `clientAuth`, `pkce`, `invalidGrant` codes such as GitHub's `bad_refresh_token`), hooks when they're behaviour (`token` reshapes a response, `metadata`, `rate.observe`). Anything weirder is a custom step.
- **Rate:** declared as `rate: { connection?, app?, observe? }`. The proxy (#23) turns them into kernel scopes and decides which instance holds `app`.
- **Webhooks:** not in the definition yet; #25 adds a `webhooks` field (verify, route to a connection by external id via #26).
- **Versioning:** none. Definitions are code, and stored state is the kernel's own (record, credential, metadata), so deploying a new definition doesn't touch live connections. In-flight handshakes carry their own data and expire in 10 min. New scopes mean the app asks for re-auth (`connect` on the same instance). A definition must keep reading metadata it wrote before; add a version field when a definition first needs a migration.
- Device code needs a `{ prompt }` start result and a timer-driven poll step; added when the first provider in #20 needs it.

## #19 First providers: GitHub, Slack, Google — decided

`packages/providers` (`@openconnect/providers`), each a `defineConnection` with tests against fakes shaped like the real responses (`fakeOAuth` + `harness` in `@openconnect/connections/testing`).

The structure (steps, helpers, metadata, rate) held. What the port changed:
- **Scopes are per-app config:** `OAuth2Config.scopes` overrides the definition's defaults, and `input.scope` overrides both. `params` can be a function of config (Slack's `user_scope`).
- **`access_token` check moved from `tokenRequest` to `credentialFrom`** (kernel), so the `token` hook reshapes first: Slack with user scopes only nests the token under `authed_user`.
- **`rate.observe(res, now)`** + `rateHeaders`: `Retry-After` (seconds or date) for all three, plus GitHub's `x-ratelimit-*`.
- **Overriding one step is a spread:** `{ ...oauth2(spec), revoke }`. GitHub needs it (`DELETE /applications/{id}/grant`, not RFC 7009), and so does Slack (`auth.revoke`).

Per provider:
- **GitHub:** OAuth Apps and GitHub Apps in one definition (expiry is optional). PKCE S256. `bad_refresh_token` → `invalid_grant`. The REST API needs a `User-Agent`. Metadata `{ id, login }` from `/user`.
- **Slack:** comma scopes, bot token as the credential, user token lifted up when only user scopes are asked for. Rotation is handled when the app turns it on. PKCE off until confirmed. Metadata `{ teamId, ... }` from the token response; `teamId` is what webhooks route by (#25, #26). Rate is one Tier-3 budget for now; per-method tiers wait for the proxy (#23).
- **Google:** `access_type=offline` + `prompt=consent` so every authorization returns a refresh token; refresh tokens don't rotate (the kernel keeps the old one). Metadata `{ sub, email }` read from the `id_token` without a signature check (it comes straight from the token endpoint over TLS).

## #22 Generic ConnectionDO — decided

`packages/runtime` (`@openconnect/runtime`). `runtime({ definitions, settings, extensions })` returns `program` (runs in every connection instance) and `fetch` (the Worker in front). `@openconnect/runtime/cloudflare`: `cloudflare(rt, { binding })` gives the DO class and the Worker's fetch; nothing else touches Cloudflare, so everything else is tested on the memory driver.

- **Loading definitions:** self-host bundles them; the registry is a plain `{ [id]: definition }` passed in. The instance key is `conn:<def>:<id>` (`instanceOf`), so a DO knows which definition to run with no lookup. The program builds `bind` lazily on the first event, after `settings()` resolves (keys, state key, API key, redirect URI, connector config per definition id). Settings load once per isolate: Workers can't do crypto at global scope. Managed loads user code differently (#34).
- **Isolation:** definition code only gets `ctx` (config, fetch, redirectUri, now). It never sees the driver, the keys or other connections, and the kernel owns every write. That's as far as it goes in one isolate: a definition can still hang or burn CPU (workerd's limits apply). Real isolation is the managed sandbox (#34).
- **When user code throws:** every user hook runs before the kernel's `cas` (`start` before the handshake opens, `metadata` before `activate`, `refresh` before `update`), so a throw leaves the record as it was. Provider `revoke` failing is logged; the connection is revoked locally anyway. The one thing a failed callback uses up is its handshake, which is single-use anyway; the app calls `connect` again.
- **Errors as data:** error classes don't survive a DO RPC, so connection methods reply `{ ok } | { error: Fault }` with `{ code, status, message, state?, reason? }`. `Fail(code, status, msg)` for runtime and extension errors, `InputError` (new in L2 for missing apiKey fields and unknown `state`) → 400, `NotActive` (now also from `connect` on a revoked connection) / `IllegalTransition` → 409, `OAuthError` → 400 (502 when the provider 5xx'd), anything else → 500 `error` and logged. `RATE` stays raw: it's kernel-to-kernel.
- **HTTP:** the routes table is keyed by first path segment. `GET /connections/:def/:id` = status + metadata; `POST /connections/:def/:id/:method` = any connection method (`connect`, `token`, `revoke`, extensions'), JSON body = args, `kernel.*` blocked. `GET /callback` is public and routes by signed `state`. Everything else needs `Authorization: Bearer <apiKey>`. Callback answers JSON for now; a redirect back to the app comes with the SDK (L4).
- **Timers:** `kernel.refresh` goes to `bind`, then to each extension's `onTimer` until one claims it.
- Non-connection instances (app-scope rate keys on the same DO class) only answer `RATE` for now.

Extension points for #23–#26: each feature is one file in `packages/runtime/src/` exporting an `Extension` (`{ routes?, connection? }` in `runtime.ts`), passed in `extensions: [...]`. Built-in routes and methods win on a name clash.
- `routes: { <segment>: { public?, fetch(req, api, path) } }` for Worker-level endpoints (proxy `/proxy/...`, webhooks `/webhooks/...`). `api.call(instance, method, args)` reaches a connection and returns a `Reply`; `reply(r)` turns it into a Response. Throw `Fail` for an HTTP error.
- `connection(hosted) => { methods?, onTimer?, after? }` per connection instance. `hosted` = `{ d, instance, def, id, bound, settings }`; `bound.conn` is the kernel connection (`events.pending()` / `ack(seq)` for #24). `methods` are reachable by RPC and over HTTP; `onTimer` claims timers named `<extension>.<name>`; `after(cause)` runs after every method and timer, failed ones too, so events delivery (#24) and the index (#26) can follow state changes.

## #26 Connection index & querying — decided

`packages/runtime/src/directory.ts`: an `Index` (`upsert`, `list`), `memoryIndex()` for tests and dev, and `directory(index)`, the extension that keeps it current. `d1Index(binding)` in `/cloudflare` is the D1 one; schema in `packages/runtime/migrations/0001_index.sql`.

**D1 schema.** `connections (def, id, state, reason, external JSON, created_at, updated_at, version)`, primary key `(def, id)`, plus `connection_external (def, key, value, id)`, one row per external id. Nothing secret is copied: the credential stays sealed in the DO.
- **External ids:** a definition declares `external(metadata) => Record<string, string>` (new optional field in `defineConnection`): Slack `{ teamId }`, GitHub `{ id }`, Google `{ sub }`. They're indexed `(def, key, value)`, not unique: one Slack team can have several connections (one per app user). Webhooks (#25) route with `findByExternal(index, def, key, value)` (or `api.index` from a route).
- **List:** `GET /connections?def=&state=&q=&external=key:value&cursor=&limit=` (API key), `{ connections: Row[], cursor }`. Ordered by `(def, id)`; keyset cursor (opaque, base64url of the last key), `limit` 1–200, default 50. `q` is a case-insensitive substring of the id or any external value; it scans (FTS5 when lists get big). `/connections` with no segment lists; `/connections/:def/:id` is unchanged. The built-in route handles both, and lists only if an extension provided an index (`Extension.index`, handed to routes as `api.index`); without one it's a 404 as before.
- One deployment = one app (#22), so there is no app/tenant column yet; managed adds one with multi-app (#34).

**Consistency.** The ConnectionDO is the source of truth; the index is a copy, eventually consistent.
- **Write path:** the extension's `after()` reads the record and the metadata, and upserts the row after every method and timer, failed ones too. `version` = the DO's store version (record or metadata, whichever is newer; the driver's per-instance counter orders both), and the upsert only replaces a row with `version <= excluded.version` (in D1: `ON CONFLICT ... WHERE`, external ids moved in the same batch). So writes that arrive out of order (interleaved `after`s, retries) never roll a row back. Calls that changed nothing (`token`, `status`) skip the write.
- **Failures:** an upsert that throws is logged by the host and doesn't fail the call. The row catches up on the next call or timer on that connection (the skip only remembers successful writes). `POST /connections/:def/:id/index.sync` forces a re-copy of one connection: the repair path for a lost or restored database.
- **Follow-ups:** `after()` first compares the kernel's `conn.version()` (the record's store version, no decrypt) and the metadata version with the last one synced, so unchanged calls (two per proxied request) cost two store reads. When the version moved but state, reason and external ids didn't (a token refresh, a re-auth to the same account), the write is skipped, unless a write from this instance is still in flight. The stored row keeps its older version, which stays monotonic: any later change carries a higher one. A throwing `external` hook is logged and falls back to the last ids written from this instance (or `{}`), so the row keeps tracking state.
- ponytail: no full rebuild. A DO namespace can't be enumerated, so rebuilding from nothing needs a list of instances; that's the index itself, or a log of creations (#24's events). Add a bulk `sync` over a list of ids if a restore ever needs it.
- ponytail: the upsert is awaited inside the call, so D1 latency lands on the caller; move it to `waitUntil` if it shows.
- Doesn't read or ack the event outbox; that's #24's.
- No delete: connections are never deleted (revoked is terminal).

**Deploy (#31):** a D1 database bound as the name passed to `d1Index` (`INDEX` in the tests), with `migrations/0001_index.sql` applied (`wrangler d1 migrations apply`, `migrations_dir = "packages/runtime/migrations"`).

## #23 Proxy — decided

`packages/runtime/src/proxy.ts`: `proxy({ timeoutMs? })` is one Extension (route + connection methods), passed in `extensions: [proxy()]`.

- **Route:** `ANY /proxy/:def/:id/<path>?<query>` (API key required) → `<def.proxy.baseUrl>/<path>?<query>`. Method, headers and body pass through; our `Authorization`, `Host` and `Content-Length` are dropped. The path goes on raw (still encoded, trailing slash kept); the incoming URL is already normalized, so it can't climb out of the base path. Redirects come back as they are (`redirect: "manual"`), never followed with the credential on. The SDK (#28) builds `oc.connection(id).fetch()` on this route.
- **Definition field:** `proxy?: { baseUrl, inject? }` on `defineConnection`. GitHub `https://api.github.com` (hook adds the required `User-Agent`), Slack `https://slack.com/api`, Google `https://www.googleapis.com`.
- **`prepare()` = permit + token in one round trip:** connection method `proxy.prepare` returns `{ credential }` or `{ retryAfterMs }`. Token first (refreshed on demand if inside 60s of expiry, `NotActive` → 409 before any permit is spent), then `acquire` over the definition's scopes: `rate.connection` on the connection instance itself (local, no hop), `rate.app` on instance `app:<def>` via the kernel's `RATE` call. All or nothing, as in #9. The credential crosses to the Worker; the body never enters the DO.
- **Auth injection:** `inject` is `{ header, prefix?, field? }` (default `Authorization: Bearer <accessToken>`), `{ query, field? }`, or a hook `(url, headers, cred) => void` for anything else (basic auth, signing, extra headers). For a static credential, the value is `fields[field]`, default its first field.
- **Rate enforcement:** a deny is our own `429` with `Retry-After` (seconds, rounded up) and `{ error: { code: "rate_limited", retryAfterMs } }`; the provider is never called. No queueing (#9): waiting is the caller's (SDK) choice. A provider's own 429 passes through untouched.
- **Header sync:** after the response headers arrive, the Worker sends status + headers to `proxy.settle`, which runs the definition's `rate.observe` and tightens the connection scope (`Retry-After`, `remaining`/`reset`). Only when the definition has `observe`. A definition with only `observe` (Google) gets an effectively unlimited connection scope so provider signals still hold.
- **Streaming and large bodies:** both bodies are streams straight through the Worker (`duplex: "half"`); nothing is buffered, so size is bound only by Workers' request limits. `Content-Encoding` / `Content-Length` are dropped from the response, since `fetch` has already decoded it.
- **Timeouts:** `timeoutMs` (default 30s) covers the wait for response headers only; a long download keeps streaming. Timeout → `504 upstream_timeout` (permit kept: the request may have reached the provider). Network error → `502 upstream_error` and the permits are refunded.
- **Internal methods:** `proxy.prepare` hands out the credential and `proxy.settle` can refund permits, so neither is reachable over `POST /connections/:def/:id/:method`. An Extension lists such methods in `internal: string[]`; the HTTP layer refuses them with 404 (like `kernel.*`), RPC from the extension's own route still works. Other extension methods stay public (`index.sync` is a repair route).
- **Settle never fails the request:** `proxy.settle` (header sync or refund) is bookkeeping; a fault or a thrown DO call is logged and the upstream response still goes back, since a non-idempotent request may already have gone through.
- Shortcuts (`ponytail:` in the code): one fixed base URL per definition (a per-connection host like Salesforce `instance_url` needs `baseUrl` as a function of the credential); Google APIs on their own hosts aren't reachable yet; the app scope is per definition since there's one app per deployment; `settle` is awaited before answering (move to `waitUntil` once routes get the execution context); provider-wide signals only tighten the connection scope; Slack's per-method tiers still share one budget.

## #24 Events / trigger delivery — decided

`packages/runtime/src/events.ts`: one `Extension` factory (`events()`, like `proxy()` and `directory(index)`), plus `src/signature.ts` (`@openconnect/runtime/signature`). On when `settings.events = { url, secret }` is set; otherwise every part of it is a no-op.

- **Delivery:** `POST settings.events.url`, JSON body = one `ConnectionEvent`, 10s timeout. Any 2xx acks; anything else (3xx, 4xx, 5xx, network error, timeout) is a failure. Redirects are never followed (`redirect: "manual"`): a followed 302 turns the POST into a GET, acks falsely and sends signed headers elsewhere. Sent through `settings.fetch` when set (tests), else global `fetch`.
- **Signature:** the [Standard Webhooks](https://www.standardwebhooks.com) scheme, so existing libraries verify it too. Headers `webhook-id` (event id), `webhook-timestamp` (unix seconds of this attempt), `webhook-signature: v1,<base64 HMAC-SHA256(key, "<id>.<timestamp>.<body>")>`, several space-separated during secret rotation. Secret = `whsec_` + base64 key. `verify(secret, headers, rawBody, { now?, toleranceSec = 300 })` in `signature.ts` (no imports, Web Crypto only), checked against the spec's test vector; the SDK (#28) re-exports it.
- **At least once:** the event leaves the outbox only after a 2xx. A crash between the 2xx and that write resends it. `id` = `<instance>:<seq>` (e.g. `conn:github:u1:7`) is the same on every attempt, so receivers dedupe on `webhook-id`.
- **Retries: DO timers, not Cloudflare Queues.** Ordering and the outbox already live in the connection's DO, so a durable timer (`events.retry`) is enough: equal-jitter backoff from `schedule.backoff`, 10s base, capped at 1h, retried indefinitely. Queues would add a binding, a consumer Worker and a second copy of the event, and give up per-connection order (a Queue delivers per batch with its own retries and DLQ), for throughput we don't need: delivery is per connection and naturally sharded across DOs. It would also tie self-host to Cloudflare. ponytail: no dead-letter and no replay API; an endpoint that stays down gets one attempt per connection per hour, and the outbox keeps the newest 1000 events; one event must fit one stored value (2 MB on DOs), so #25 truncates or stores a reference past that. Dashboard replay comes with L4.
- **Ordering:** strict per connection. One outbox per connection, delivered head first, one in flight; a failure parks the whole outbox (later events wait behind it, a new event doesn't skip the backoff). `seq` is gapless per connection except when the 1000 cap drops events. No order across connections.
- **Storage:** one key per event (`events.e:<seq>`) and a small head record `events.head = { seq, done, kseq, attempt, retryAt }`. One value per event keeps every write small (a single-value outbox hits the 2 MB DO value cap with a big backlog, and redraining it is O(N²) bytes). The head's `cas` is the commit point: events in `(done, seq]` are live. An append writes keys past `seq`, then cas'es `seq` and `kseq` together; a crash before that leaves keys that the next append overwrites, and the kernel events are still un-acked, so nothing is lost or duplicated. Delivery cas'es `done` forward after a 2xx, then deletes the key. Past 1000 live events an append moves `done` up and deletes those keys. Appends (copying kernel transitions in, `emit`) are serialized per instance in memory, since keys past `seq` are uncommitted; delivery only touches `done`/`attempt`/`retryAt`, so it races appends safely through the cas.
- **Where it runs:** `after()` (every method and timer) first reads the kernel's event seq (`conn.events.seq()`, a new kernel accessor that reads the record without decrypting) and stops if it hasn't moved since the last call; most calls (token, proxied requests) end there. Otherwise it copies new transitions in, acks them in the kernel, and arms `events.retry` (now, or at the parked retry time). The POSTs happen in `onTimer`, so a slow endpoint never holds up the method that caused the event, and timers don't overlap within an instance. A transition whose `after()` never ran (instance evicted mid-method) waits for the next call or timer on that connection; the first `after()` in a fresh isolate always copies and arms, which also covers a timer lost after a failure.
- **Separate outbox, not a kernel change:** the kernel outbox stays transitions-only, capped at 100, inside the record's `cas`. Webhook events don't belong in the credential record (they'd bump its version and contend with refresh), and delivery state (attempt, retry time) isn't the kernel's business. The cost is one extra key write per transition plus the head write.
- **Catalog** (`ConnectionEvent` = `LifecycleEvent | WebhookEvent`, common fields `{ id, seq, at, connection: { definition, id } }`):
  - `connection.pending | connection.active | connection.reauth_required | connection.revoked`, one per state change, `data = { from, to, reason? }` straight from the kernel (`from: null` = created). Refreshes that keep the connection `active` aren't events: they aren't state changes, and they'd be most of the traffic. Reasons today: `invalid_grant`, `refresh_failed`, `expired`, a revoke reason.
  - `webhook`, `data` = whatever #25 emits. #25 calls `emit(hosted, data)` from its connection method (the Worker route reaches the connection with `api.call`); it is ordered after every transition so far on that connection. #25 decides the shape of `data` (provider, topic, payload).

## #25 Webhook ingress & auto-registration — decided

`packages/runtime/src/webhooks.ts`: one Extension factory, `webhooks()`, next to `events()` (it delivers through #24's outbox, so it needs `settings.events`) and `directory(index)` (app-level routing needs the index). Definitions get a `webhooks` field in `defineConnection`.

- **Ingress URLs.** Both public (no API key): the provider's signature is the authentication, checked in the Worker before anything reaches a connection.
  - `POST /webhooks/:def/:id`: one connection's webhook, the URL a per-connection subscription points at (GitHub repo/org hooks, Google channels).
  - `POST /webhooks/:def`: one URL for the whole app (Slack's Events API Request URL). The definition's `parse` names the account (`external: { key, value }`, the same key `external(metadata)` indexes, #26); the route looks it up with `findByExternal` and fans out to every non-revoked connection with it, in parallel (Slack wants an answer within 3s). No match = `200 { delivered: 0 }`, so the provider doesn't retry or disable the URL. Without an index the app route is a 503.
- **Definition field** `webhooks: { verify, parse, register?, unregister? }`:
  - `verify(ctx, { headers, body }, secret)`: `body` is the raw text. `secret` is the connection's own webhook secret on `/webhooks/:def/:id`, null on the app route; app-wide secrets come from the definition's config. `ctx` is `{ config, now }` only (no fetch: verifying needs nothing else). False → 401.
  - `parse(req)` → `{ reply }` for a handshake, answered as JSON and not delivered (Slack `url_verification` → `{ challenge }`, GitHub `ping`, Google `sync`), or `{ topic, delivery?, payload, external? }`. A throw → 400.
  - `register(ctx, cred, { url, secret })` → `{ hook, expiresAt? } | null` and `unregister(ctx, cred, hook)`, for providers where a subscription is created per connection.
  - Helpers in `@openconnect/connections`: `hmacHex(secret, message)` and `safeEqual(got, expected)` (compares SHA-256 digests, so timing says nothing about the secret).
- **Per-connection secrets are derived, not stored:** `base64url(HMAC(settings.webhooks.key, "webhook:" + instance))`. Every connection's differs, so a delivery for one can't be replayed into another, and the Worker can check it without a DO round trip. ponytail: rotating `settings.webhooks.key` changes every derived secret, so every registered or app-created hook stops verifying until it's re-registered; there's no key-version list yet (as in #10) to accept the old one while hooks move over. `settings.webhooks = { url, key }`: the public base of `/webhooks` (registration needs it) and the HMAC key. `webhooks.endpoint` (connection method, API key) returns `{ url, secret }` for apps that create the provider hook themselves. Secrets are never logged; the only place one leaves is that method and the provider registration.
- **Cross-tenant guard:** a webhook signed with an app-wide secret (Slack) is valid on any URL. So when `parse` names an account, `webhooks.receive` checks it against the connection's own external ids and refuses a mismatch (403). The app route is correct by construction; the check matters on `/webhooks/:def/:id`, and it also catches a stale index row (skipped in a fan-out).
- **Into the connection:** the route calls `webhooks.receive` (internal: refused over `POST /connections/...`, like `proxy.prepare`; only the route that verified may call it), which checks the connection exists (404) and isn't revoked (410), then `emit(hosted, data)`: queued after every lifecycle event so far, delivered signed, ordered, at least once (#24). A per-connection webhook to a revoked connection gets 410, which is also what a leftover provider hook sees. Without `settings.events` the route answers 503 rather than accept and drop; handshakes still work.
- **`data` of a `webhook` event** (`WebhookData`): `{ topic, delivery, payload, truncated? }`. The provider is `connection.definition`, already on every event. `topic` is the provider's event name (GitHub `X-GitHub-Event`, Slack `event.type`, Google `calendar.<resource-state>`). `delivery` is the provider's delivery id (GitHub `X-GitHub-Delivery`, Slack `event_id`, Google `<channel>:<message-number>`), null if none. Receivers dedupe on it as well as on `webhook-id`: a provider retry is a new event with the same `delivery`. GitHub and Google deliveries carry no signed timestamp (only Slack's does, with its 5 min window), so a captured genuine delivery can be replayed to its URL; replay protection for those rests on receivers deduping on `delivery`.
- **Size:** one event must fit one stored DO value (2 MB, #24). A payload over `MAX_PAYLOAD` (1 MB of JSON) is delivered with `payload: null, truncated: <bytes>`; the receiver re-reads the resource through the proxy. ponytail: no stored reference (would need blob storage, R2); add one if large payloads (GitHub's go up to 25 MB) matter.
- **Fan-out failures:** if any connection fails to take it (a DO error, not 404/410/403), the route answers 503 so the provider retries. Connections that already took it get it again: at least once, deduped on `delivery`. No partial-ack bookkeeping.
- **Auto-registration** (definitions with `register`, deployments with `settings.webhooks`):
  - `after()` checks the record version (no decrypt, like #24 and #26); when it moved and the connection is `active` and a registration is due (nothing stored, the stored one due for renewal, or stored for another account), it arms the durable timer `webhooks.sync` now. A `webhooks.pending` key marks a sync that's armed or backing off, so version bumps (refreshes, event acks, re-auths) don't reset its backoff; a fresh isolate ignores the mark, since its timer may be lost. The version is remembered only after the check landed. The registration runs from the timer, so a slow provider never holds up `connect`/`callback`, and timers don't overlap within an instance. The first `after()` in a fresh isolate always checks, which also covers a lost timer.
  - The timer gets a fresh token (`bound.token()`), calls `register` with the connection's URL and secret, and stores `{ hook, expiresAt }` under `webhooks.hook`. Idempotent: anything stored means registered (`hook: null` = the definition chose not to register, e.g. Google without `watchCalendar`). Failures retry with `schedule.backoff` (30s base, 8 attempts); ponytail: then it gives up until the next state change or isolate restart, renewals included (a lapsed hook is due, so the next change re-registers).
  - **Renewal:** with `expiresAt`, the timer is re-armed an hour before it (for short-lived ones at half their life, never sooner than 1 min after registering, so a lapsed or near `expiresAt` can't loop); renewing registers a new subscription, then unregisters the old one. A sync that fails anywhere clears `webhooks.pending` unless it armed a retry. An `external` hook that throws makes the account unknown, which counts as no change (no re-registration).
  - **Lifecycle:** `reauth_required` keeps the subscription (it's the provider account's, and re-auth usually restores the same account); nothing is re-registered on re-activation to the same account. The stored hook remembers the external ids it was made for; a re-auth to another account registers a new one and unregisters the old (ponytail: with the new account's credential, which the provider may refuse; logged, and the old one lapses or gets 403). On `revoke`, a new host hook `beforeRevoke` (runs before the provider revoke, while the credential is still there; errors are logged and the revoke goes on) gets the credential first, then cancels the timer, takes the stored hook and calls `unregister`. Revoking from `reauth_required` has no credential: the hook is dropped with an explicit log line naming it (it can't be removed from here). A registration racing a revoke re-reads the state after storing and undoes itself. ponytail: unregister is one best-effort try with no retry, since after the revoke there's no credential to retry with; a leftover subscription gets 410 (and Google channels lapse on their own).
- **Clock:** the Worker has no driver, so `runtime({ now })` sets `api.now` (default `Date.now`); verification timestamps (Slack's 5 min window) use it, and tests pass the memory driver's clock. Connection instances keep using `d.now()`.

Per provider:
- **GitHub:** `X-Hub-Signature-256` (`sha256=` hex HMAC of the raw body) with the connection's secret, per-connection route only. `ping` is a handshake. Not auto-registered: GitHub has no account-wide hooks (only repo, org and App hooks), so which repos or orgs to hook is the app's choice; it creates them through the proxy (`POST /repos/{o}/{r}/hooks`, `content_type: "json"`) with `webhooks.endpoint`'s URL and secret. ponytail: no app-level route for GitHub App webhooks; they'd route by installation id, which isn't in the metadata or the index yet.
- **Slack:** app-level route. v0 signature (`v0=` hex HMAC of `v0:<ts>:<body>`) with `config.signingSecret`, timestamp within 5 min of `api.now`. `url_verification` answers `{ challenge }`. Routed by `team_id` → `teamId`, to every connection of that workspace. A payload without `team_id` is refused (400): the signing secret is app-wide, so the team is the only thing tying it to a connection, on `/webhooks/slack/:id` too. Nothing to register: the Request URL is set once in the app's settings. ponytail: Events API JSON only; interactivity and slash commands (form bodies) and Enterprise Grid org-wide installs (`authorizations[]`) come later.
- **Google:** it makes sense, and it's the one that needs registration: Calendar push channels (`events.watch` on the primary calendar), opt-in with `config.watchCalendar` plus a calendar scope in `config.scopes`. Google signs nothing; the channel `token` is the connection's secret, echoed in `X-Goog-Channel-Token` and compared. The body is empty: the event carries channel/resource ids and the app re-syncs through the proxy. Channels lapse (`expiration`), so they're renewed; `channels.stop` unregisters (404 = already gone). ponytail: Calendar only; Drive `changes.watch` is the same shape, Gmail needs Pub/Sub (app-level, OIDC-signed push).

Tests: `webhooks.test.ts` (memory driver, a test definition: both routes, handshakes, signature failures, cross-account refusal, fan-out with revoked rows, truncation, no `settings.events`, register retry/idempotency/renewal/unregister, re-arm after giving up (first registration and renewal), backoff not reset by state changes, re-auth to another account, a revoke racing a registration, a fan-out answering 503 when a connection call throws), provider verify/parse/register against fakes in `providers.test.ts`, and the workerd test runs both routes through the Worker, D1 and the ConnectionDOs and checks each DO's outbox.

## #28 Server SDK — decided

`packages/sdk` (`@openconnect/sdk`): a typed client over the runtime's HTTP API (#22, #23, #26) plus the receiving end of event delivery (#24). Fetch and Web Crypto only, no Node APIs, so one build runs on Node 18+, Bun, Workers and Deno; `tsconfig.web.json` typechecks it with no Bun or Node types to keep it that way.

```ts
const oc = openconnect({ url: "https://connect.example.com", apiKey });
const gh = oc.connection("github", user.id);
const { url } = await gh.connect();             // send the user to url
const res = await gh.fetch("/user", { retry: true }); // through /proxy, provider response as is
for await (const c of oc.connections.list({ state: "reauth_required" })) { ... }

const ev = oc.events({ secret: env.OPENCONNECT_EVENTS_SECRET, dedupe });
ev.on("connection.reauth_required", (e, conn) => ...).on("webhook", (e, conn) => ...);
export const POST = (req: Request) => ev.handle(req);
```

- **Address = `(def, id)`, two arguments**, not one id. The runtime's address is the pair (`/connections/:def/:id`, `Row { def, id }`, events' `connection: { definition, id }`), and apps naturally key both by their own user id (`connection("github", user.id)`, `connection("slack", user.id)`). A joined string would need an escaping rule (`id` may contain `:` and `/`). Both are path-encoded, so any id works, except `.`, `..` and empty, which would collapse the path and are refused (`bad_request`).
- **Connection methods** map one to one onto routes: `status()` (`GET`), `connect(args?)` → `{ url | null }` (null: finished inline, API keys pass their fields as `args`), `token()`, `revoke(reason?)`, `call(method, args)` for extension methods (`index.sync`, `webhooks.endpoint`). JSON in, JSON out, nothing cached client-side: the DO is the source of truth and is one round trip away.
- **Errors:** every non-2xx from the runtime throws `OpenConnectError { code, status, message, state?, reason?, retryAfterMs? }`, straight from the `{ error: Fault }` body. A non-JSON failure (a gateway's HTML 502) is `code: "http_error"`. Network errors are fetch's own, untouched. `status()` of a missing connection throws `not_found` rather than returning null: 404 also means an unknown definition, and the two shouldn't look alike.
- **`fetch(path, init)` through the proxy:** `path` is relative to the definition's base URL and goes on as written (the caller encodes). It can't climb out: URL parsing removes `..` and `%2e%2e` (any case) client-side, so `fetch("../../../connections/github/u2/token", { method: "POST" })` would reach the admin API with the API key. The SDK resolves the URL first and throws `bad_request` unless its path still starts with `/proxy/:def/:id/` (and `/connections/:def/:id/` for `call`); nothing is sent. It answers the provider's response whatever its status, like `fetch`; it throws only for what the runtime itself refused (`not_active`, `rate_limited`, `upstream_timeout`, ...). Telling the two apart needs a marker, since providers answer JSON errors too: **runtime change**, every error the runtime answers (`reply()`, the proxy's 429) now carries `openconnect-error: <code>`, and the proxy strips that header from upstream responses so a provider can't forge one. The other side of that: a failure in front of the runtime (a load balancer's 502, a WAF page) has no marker either, so `fetch` returns it as if the provider had answered; check `res.ok` as with any fetch.
- **429 retry, opt-in:** `retry: true | { attempts = 3, maxWaitMs = 60s }`. Only our own `rate_limited` is retried: it guarantees the provider was never called, so it's safe for any method. A provider's own 429 passes through (#23 already folds its Retry-After into the connection scope, so the next try gets ours). It waits `retryAfterMs` (exact; the header is rounded up to seconds) and fails at once, without sleeping, when the wait would go past `maxWaitMs`. ponytail: a `ReadableStream` body can't be sent twice, so it's never retried; buffer it to retry. Default off: a request handler that sleeps 30s is a choice the app makes. `sleep` is an option so tests drive the fake clock.
- **List:** `connections.page(query)` is one page (`{ connections, cursor }`, the runtime's `Page`), `connections.list(query)` an async iterator over every row, following cursors. `external` is `{ key, value }` as in the runtime's `Query`.
- **Types are shared, not copied:** `ConnectionEvent`, `LifecycleEvent`, `WebhookEvent`, `WebhookData`, `Row`, `Page`, `Query`, `Fault` come from `@openconnect/runtime`, `State`, `Credential`, `Json` from the kernel, all as `import type` (erased). The only runtime value imported is `verify`/`sign` from `@openconnect/runtime/signature`, which imports nothing; a test asserts both, so the SDK never bundles runtime code. ponytail: the package still depends on `@openconnect/runtime` (and the kernel) for those; split `signature.ts` (and the shared types) into their own package before publishing, so installing the SDK doesn't install the runtime.

**Events.** `oc.events({ secret, dedupe?, toleranceSec?, now? })` gives `on(type, handler)` and `handle(Request) → Response`.
- `handle` reads the raw body, `verify`s it (Standard Webhooks, 5 min tolerance) → 401; parses it → 400 (a signed body that isn't JSON can't come from a genuine runtime, but if it did, a 400 isn't a 2xx: it would park that connection's later events behind it, like a throwing handler); runs the handlers for its `type`, then `"*"` ones, in registration order, awaited one by one → 204. A throw → 500 and logged, so the runtime keeps the event and retries it with the same `webhook-id`. No handler for a type is still a 204: otherwise the runtime would retry an event the app doesn't care about forever, and block that connection behind it.
- Handlers get the typed event (`on("connection.active", e => e.data.from)` narrows through `EventOf<T>`) and the event's connection as a client (`conn.fetch`, `conn.status()`), which is why `events` hangs off `oc` rather than being free-standing. That's also the only reason it needs `url`/`apiKey`: verifying needs only the secret. The connection's state is "now", not the event's (an event is history: by delivery the connection may have moved on).
- **Ordering means a failing handler blocks:** delivery is strictly ordered per connection (#24), so a handler that keeps throwing parks that connection's later events (retried up to 1h apart, newest 1000 kept). Handlers should throw only for what a retry can fix (database down) and catch the rest.
- **Dedupe hook:** `dedupe: { has(id), add(id) }` on `webhook-id`, checked before the handlers and recorded only after they all succeed, so a failed attempt is retried rather than swallowed. A `Set<string>` fits it (dev); production passes a shared store with a TTL. Two copies arriving at once can both run: at least once, not exactly once. Webhook events also carry the provider's `data.delivery` (#25), which a provider retry repeats under a new `webhook-id`; deduping on it is the handler's call, since only some apps care.
- **Framework adapters: none, except Node.** `handle` is `(Request) => Promise<Response>`, which already is a Next route handler (`export const POST = ...`), a Hono handler (`c => ev.handle(c.req.raw)`), and Bun/Deno/Workers' `fetch`. Express and `node:http` speak `(req, res)`, so `@openconnect/sdk/node` has `toNode(handle)` (~30 lines, typed structurally: no `@types/node` and no Node import). The request URL uses a fixed origin (`http://localhost` + `req.url`): the Host header is the client's to write, and a malformed one would make `new Request` throw. Everything is wrapped in a try/catch that logs and answers 500, since Express 4 and `node:http` don't catch a rejected handler and an unhandled rejection kills the process. It takes the raw body from the stream, or from `express.raw()`'s Buffer; a body a JSON parser already consumed can't be verified, so it answers 500 with a log line saying to mount it before `express.json()` (500, not 400: the event waits until the app is fixed instead of being lost). Fastify and Koa can wrap `handle` the same way in a few lines; add them when someone asks.

Tests (`packages/sdk/src/*.test.ts`) run the SDK against the real runtime in process: `testing.ts` builds `runtime()` with the memory driver, `proxy()`, `events()`, `directory(memoryIndex())` and fake providers (`fakeOAuth`), and points the SDK's `fetch` at the runtime's fetch handler and the runtime's event delivery at the SDK's `handle`. Covered: path traversal (`..`, `%2e%2e`, `%2E%2e`, `.`/`..` as def, id or method), oauth2 and API-key connect/status/token/revoke, error codes (not_found, bad_request, internal methods, wrong API key, a non-JSON gateway error), list filters and cursor iteration, proxy pass-through (provider errors returned, forged marker stripped), 429 thrown / over budget / stream body / retried after the exact wait, real signed deliveries with typed dispatch and handler callbacks, bad signature / wrong secret / stale timestamp, a throwing handler retried in order, dedupe, and the Node adapter (including a malformed Host and a throwing handler).

Open: `/callback` still answers JSON; the redirect back to the app (a return URL per `connect`) lands with the frontend connect UI (done in #29: return URL per session). No CLI-side or browser SDK yet (#27).

## #29 Frontend connect UI — decided

`packages/runtime/src/session.ts` (`sessions()` Extension, on when `settings.sessions = { key, origins }` is set) and `packages/connect` (`@openconnect/connect`): zero dependencies, browser APIs only (`tsconfig.web.json` checks it with the DOM lib and no Bun types). The SDK gets `connection(def, id).session(...)`.

```ts
// app backend (API key)
const { token } = await oc.connection("github", user.id).session({ origin: "https://app.example.com" });
// app page
button.onclick = async () => {
  const r = await connect({ url: "https://connect.example.com", token }); // { status: "connected" | "error" | "closed" | "redirecting" }
};
const back = await resume({ url, token }); // on the return URL's page (redirect mode)
mount(el, { url, token, onResult }); // prebuilt: a button, or a form for API-key definitions (runs resume() too)
```

**The flow.** `connect()` opens a blank popup → `POST /session/authorize` (fetch, session token) → a single-use ticket → the popup (or the page, in redirect mode) navigates to `GET /session/authorize?ticket=` → binding cookie + `303` to the provider → `/callback` exchanges the code but doesn't activate → hands a single-use `completion` to the app's page (posted to `window.opener`, or in the return URL's fragment) → the page confirms it, `POST /session/complete`, with its own token → activated.

- **Popup by default, redirect as the fallback.** A popup keeps the app's page and state, and the result comes back as a value. Redirect is there for popup blockers, mobile, and providers whose pages cut the opener. `connect()` opens the popup before awaiting anything (blank, named), so it must run inside the click; `token` may be a function, awaited after the popup opened. A blocked popup redirects instead if the session has a `returnUrl`, else it's `popup_blocked`. A popup closed while the token or ticket was being fetched isn't navigated (that would open a tab): `closed`.
- **Session token, no database.** `POST /connections/:def/:id/session` (API key, connection method `session`, runs in the instance with `d.now()`, so a revoked connection is refused there) returns `{ token, expiresAt }`: `sign(JSON({ typ: "openconnect.session", def, id, exp, origin, returnUrl? }), settings.sessions.key)`, the kernel's HMAC format. A separate key from `stateKey`, and a `typ` a state can't have. TTL 10 min by default, 1 s..1 h. Signed, not secret: the browser package reads `returnUrl`, `def` and `id` from it. Issue checks `origin` (or `returnUrl`'s origin, the default) and `returnUrl`'s origin against `settings.sessions.origins`, exact origins only; `returnUrl` must be http(s) and have no fragment (the outcome goes there).
- **What a token can do: start and confirm one connection's authorization, nothing else.** It is not an API key: every other route still wants the API key (no `token()`, no proxy, no status beyond the state). The routes, `Authorization: Bearer <session token>`, CORS for the token's origin only (`Vary: Origin`, no credentials, preflight for allowlisted origins); a request whose `Origin` isn't the token's is a 403:
  - `GET /session` → `SessionInfo { definition, id, flow: "redirect" | "form", fields, state, reason?, expiresAt }`. `flow` is `form` when the definition has no callback step; `fields` comes from a new `Auth.fields` that `apiKey(fields)` sets.
  - `POST /session/connect` `{ fields }` → `{ state, reason? }`, `form` flows only. No metadata, no credential.
  - `POST /session/authorize` `{ mode, nonce }` → `{ ticket }`, `redirect` flows only.
  - `POST /session/complete` `{ completion }` → `{ state, reason? }`.
  - `GET /session/authorize?ticket=` (navigation, no CORS).
  - Internal methods `session.ticket`, `session.authorize`, `session.complete`, refused over `/connections`.
- **Why a fetch and a ticket, not a form POST.** The first version submitted the token in a form to `/session/authorize` and checked its `Origin`. A form POST from a page with a strict `Referrer-Policy` (`no-referrer`, `same-origin`: helmet's default) sends `Origin: null`, so every flow failed. A fetch always sends the real `Origin`. The navigation that follows carries a ticket: `sign({ typ: "openconnect.ticket", def, id, t })`, with `t` stored in that connection's instance for 60 s (with mode, nonce, origin, returnUrl) and taken once. So the token stays out of URLs, and a ticket can't be reused, outlive its minute, or be used on another connection (its id exists only in its own instance). The ticket's response has `Referrer-Policy: no-referrer`. Errors before the provider (expired token, wrong origin, revoked connection at mint) come back to `connect()` in the opener, which closes the popup.
- **Login CSRF: confirmed by the app's page, finished in the browser that opened the ticket.** Our `state` names a connection, not a browser. A user of the app could start a flow on their own connection and get a victim's browser through it; a provider that auto-approves returning users would then put the victim's account on the attacker's connection. `Origin` alone can't stop this once tickets exist: a ticket can be minted outside a browser with a forged `Origin`, then sent to a victim as a link. Two checks:
  - **Confirm step.** With a session handshake, `/callback` runs the definition's callback (the code exchange) but doesn't activate: the credential waits sealed (`encrypt`, `session.done:<completion>`, 10 min, single use) in the instance, and the callback hands `completion` only to the app's origin in the browser that logged in: `postMessage` to the opener with `targetOrigin` = the session's origin, or in the session's return URL's fragment. Activation (`metadata`, then `activate`, via `bind.finish`) happens on `POST /session/complete` with a session token for that same connection, from the session's origin. A connection revoked meanwhile is refused (`not_active`) before `metadata` calls the provider with the new credential. Two completions pending for one connection (two tabs): each confirms once, and the last confirmed wins, as with any re-auth. ponytail: a completion never confirmed (the page was closed) expires after 10 min and leaves a code already exchanged, an unused grant at the provider; revoke it at the provider on expiry (a timer in the instance) if that matters. In the attack the completion lands on the app's page in the victim's browser, whose session is the victim's own connection: refused (`bad_completion`), and the attacker never sees it. `bind` gains `exchange(params, hs)` and `finish(cred)` (the old `callback` is both); a handshake opened without a session still activates at the callback as before.
  - **Binding cookie.** `GET /session/authorize` sets `oc-<random>=<random>` (`HttpOnly; Secure; SameSite=Lax; Path=<callback path>; Max-Age=600`), stored with the handshake. The callback route hands the request's Cookie header to the instance (under a reserved key that overwrites any query parameter of that name), which compares it before the exchange: `session_mismatch` (403). This covers the provider URL itself being sent to a victim. Lax is sent on the provider's top-level redirect back, and a cookie set by a top-level response is first-party.
- **Callback completion.** `bind.connect(input, extra)` stores the session's `Target { mode, origin, returnUrl?, nonce, cookie, definition, id }` with the handshake and `bind.handshake(params)` takes it back, so the callback knows where to go with no lookup. The instance's `callback` replies `{ target, completion }` or `{ target, error }` (errors as data, so a provider's `access_denied` still reaches the app); `/callback` clears the cookie and:
  - `redirect` → `303` to the bound `returnUrl` with the outcome in the fragment: `#openconnect=authorized&definition=<def>&id=<id>&completion=<c>&nonce=<n>` or `#openconnect=error&definition=…&id=…&code=<code>&nonce=<n>` (its query kept). A fragment never reaches a server or a `Referer`. `resume()` on that page takes it only if `definition`/`id` match its token's claims (a page with a GitHub and a Slack button: each takes its own, the other gets null, not `bad_completion`), removes our keys with `history.replaceState` (so a reload, the history entry or a later third-party script finds nothing) and confirms. On a reload with nothing there it does nothing. An outcome for another connection is left alone; on a victim's page in the CSRF case above it stays in the fragment until the completion expires, readable by script on the app's origin (which owns the user anyway).
  - `popup` → a tiny page that posts `{ type: "openconnect", nonce, definition, id, status: "authorized", completion }` (or `status: "error", code, message`) to `window.opener` with `targetOrigin` = the bound origin, then closes. With no opener (a provider page with COOP `same-origin` cuts it) it goes on to the return URL if the session has one, where `resume()` confirms and closes the popup. Text HTML-escaped, the JSON in the script escapes `<`, `>`, `&`, U+2028/9 (a provider's `error` parameter lands in it), CSP `default-src 'none'; script-src 'nonce-…'`, `no-store`, `no-referrer`, `nosniff`. The client accepts a message only from the runtime's origin, from that popup window, with its nonce.
  - Without a target (handshakes from the API-key `connect`, #28) it's the JSON reply as before. #28's `connect()` URL isn't tied to a browser, so it stays exposed to login CSRF; its doc comment says to use sessions for browser flows.
- **Open redirect:** the only place the callback redirects is the `returnUrl` bound into the token at issue; no request can change it. The allowlist is checked again on the way back, so narrowing `origins` takes effect at once: a target no longer allowed gets a JSON 403, not a redirect or a post.
- **Replay:** a session token is reusable until it expires, for one connection, from one origin: a retry after closing the popup needs no new token. Tickets and completions are single use. What a stolen token allows is starting and confirming an authorization of that connection: with the user's own browser account, that needs script on the app's origin, which already owns the user. ponytail: no single-use session tokens or revocation list; no rate limit on `/session`.
- **Garbage input never 500s:** the kernel's `verify` returns null for malformed base64 (it threw), and `routeState` for a payload that isn't an array; a bad token, ticket or `state` is a 401/400.
- **Headless and prebuilt.** Headless: `connect(opts) → Promise<Result>` (popup, redirect, or `fields` through fetch; never throws), `resume()` on the return URL, `session()` (`GET /session`), `claims()`. Prebuilt: `mount(el, opts) → unmount`, an unstyled button (or, for `form` flows, a form with one input per field, `password` for names like key/secret/token) with `oc-*` classes and an `aria-live` status; it runs `resume()` first. A function, not a Web Component: no global registry, no attribute/property sync, nothing runs at import (SSR-safe), and it works from any framework. React: `useEffect(() => mount(ref.current!, opts), [])`, or call `connect()` from your own button. A `<openconnect-button>` wrapper is a few lines when someone asks. ponytail: field labels and types are guessed from names; give `apiKey` labeled fields when a provider needs them. `SessionInfo` is copied into the browser package to keep it dependency-free; move it with the SDK's shared types (#28's ponytail).
- **Closed popups, and COOP.** A provider page with `Cross-Origin-Opener-Policy: same-origin` cuts the popup from its opener: Chromium reports `popup.closed` the moment the popup gets there, while the user is still logging in, and the callback page has no opener to post to. So:
  - The callback page with no opener goes on to the return URL (if the session has one). The fragment also carries the attempt's `nonce` (not secret). `resume()` there confirms, then posts the result on `BroadcastChannel("openconnect:<nonce>")`: same origin as the app, so only the app's pages hear it, and it carries the result only (the completion is already used). `connect()` listens on that channel while it waits.
  - Closed is ambiguous, so `connect()` uses timing. A popup that reads as closed within 5 s of going to the provider is taken as COOP: it keeps waiting (the channel, plus `session()` every 2 s) until the connection is active (`connected`), revoked, or `timeoutMs`, then `closed`. A popup closed later is the user: one look at the state (`connected` if active), then `closed` within a second. Polling covers a browser without BroadcastChannel.
  - ponytail: a user who cancels within the first 5 s gets `closed` only at `timeoutMs` (default 10 min); pass a smaller `timeoutMs` if that matters. A provider whose COOP page comes after 5 s (a non-COOP login page first) is reported `closed` while the popup may still finish on the return URL (the connection still activates; the app's next `session()` shows it). Under COOP the popup's `window.name` is cleared (a new browsing context group), so `resume()` there can't tell it's the popup and doesn't close it; the app's page shows its connected state in it.
  - A `connected` broadcast is believed only after one `session()` check says active (any of the app's pages could post on the channel). A terminal session error during the wait (`session_expired`, `unauthorized`, `forbidden`, `not_found`) ends it as `closed`.
  - `connect({ signal })` takes an `AbortSignal`: aborting closes the popup and resolves `{ status: "error", code: "aborted" }`. `onClosed()` fires once the popup reads closed. `mount()` uses both: the button is enabled again as soon as the popup reads closed (the wait goes on in the background), and a second click aborts the first attempt, whose result is dropped.
  - One poll tick of grace after a close, since the callback page posts and then closes. A timeout with the popup still open closes it (`timeout`).
- **Limits:** the callback must be a GET (Lax cookies aren't sent on a cross-site POST, so `response_mode=form_post` would need `SameSite=None`). `Secure` cookies need https, or `localhost`. The message origin is the runtime URL's origin, so `/callback` must be on the same origin as the `url` the page uses. A credential the app's page never confirms (page closed mid-flow) expires with the completion after 10 min; the connection stays as it was. No per-session input (scopes) yet: bind `input` into the token when an app needs per-user scopes.

Tests: `session.test.ts` (memory driver: issue + allowlist + TTL; `GET /session` with CORS; preflight; forged, state-shaped, expired and malformed tokens, tickets and states (never a 500); the token refused on admin, token and proxy routes and the internal methods; the API-key form; tickets single use, 60 s, one connection, minted only from the token's origin (`Origin: null` refused) and navigated with no Origin or Referer; popup page with completion and the confirm (single use); redirect; provider errors; COOP fallback to the return URL; login CSRF with a ticket minted outside a browser and opened by a victim, by the provider URL with no cookie, by a smuggled or wrong cookie; open redirect after the allowlist narrowed; HTML/script escaping; JSON callback unchanged). `packages/connect` tests drive `connect()`, `resume()` and `mount()` with a fake window (DOM elements, `window.open`, `location`, `postMessage`, timers) in front of the real runtime; navigations carry no Origin or Referer, as from a `no-referrer` page: synchronous open, token function, errors in the opener, closed before navigating, message filtering by origin/source/nonce, closed, timeout, COOP via `resume()` in the popup, popup-blocked fallback, redirect and `resume()`, fields. `e2e/chromium.ts` runs the flows in a real Chromium across two sites, the app page served with `Referrer-Policy: no-referrer`: popup with a given and a fetched token, a popup the user closes, the API-key form, a COOP `same-origin` provider page, redirect mode, and a ticket minted outside a browser that a victim (logged in to the app as someone else) opens, never activated. It needs Playwright, so it isn't part of `bun run test`.

## #30 CLI `openconnect dev` — decided

`packages/cli` (`@openconnect/cli`, bin `openconnect`). `openconnect dev` runs the whole runtime (every built-in extension) on the memory driver with a real clock, served by `Bun.serve`, from the project's `openconnect.config.ts`; state is kept in `.openconnect/` across restarts, and a save reloads the definitions in place.

```ts
// openconnect.config.ts
import { defineConfig } from "@openconnect/cli";
import { github } from "@openconnect/providers";
export default defineConfig((env) => ({
  definitions: [github, myOwnDefinition],
  config: { github: { clientId: env.GITHUB_CLIENT_ID, clientSecret: env.GITHUB_CLIENT_SECRET } },
  events: { url: "http://localhost:3000/api/openconnect" }, // optional
  sessions: { origins: ["http://localhost:3000"] },         // optional
  extensions: [],                                           // optional, after the built-in ones
}));
```

**Project shape (`src/project.ts`), the input `deploy` (#31) bundles too.** A `Project` is `{ definitions: Definition[], config?, events?: { url }, sessions?: { origins }, extensions? }`, or a function of the environment returning one. Not `runtime()`'s options directly: those hold keys and a settings loader, which differ per host, while the project is what the user writes once. Definitions are an array keyed by `def.id` (a registry object could disagree with the ids; duplicates are an error). `config` defaults to null for definitions with no callback step (`apiKey`); an OAuth definition with no config is listed as such in the banner and answers `not_configured`, as before. Everything secret or per-host comes from the environment, so one config works in dev and deployed:
- `OPENCONNECT_PUBLIC_URL` (→ `redirectUri` = `<url>/callback`, `webhooks.url` = `<url>/webhooks`), `OPENCONNECT_API_KEY`, `OPENCONNECT_KEY_V<n>` (encryption keys by version, the highest is current, #10), `OPENCONNECT_STATE_KEY`, `OPENCONNECT_SESSIONS_KEY`, `OPENCONNECT_WEBHOOKS_KEY`, `OPENCONNECT_EVENTS_SECRET` (`whsec_…`). A missing one fails at load with its name.
- `options(config, env, index)` returns `runtime()`'s input: the registry, a memoized `settings()` and the extensions `[proxy(), events(), webhooks(), sessions(), directory(index), ...project.extensions]` (each a no-op until its setting is set). The index is the host's: `memoryIndex()` in dev, `d1Index` deployed. `generateKeys()` makes every generated secret (dev writes them to a file, deploy sets them as Worker secrets). `project.ts` imports no Node or Bun API, so the deployed Worker can import it.

**Env and keys.** Lowest to highest: generated keys (`.openconnect/dev.vars`), `.env`, `.dev.vars` (wrangler's file, so the same one works under `wrangler dev` and deploy can push it), the process environment. Dev keys are generated on the first run, never replaced (missing ones are added), written `0600`, so sealed credentials, signed states and the API key stay valid across runs. The banner prints the API key and says where the events secret is. `.openconnect/` writes its own `.gitignore` (`*`), so nothing in the user's repo needs editing.

**Local runtime: the memory driver under Bun, not workerd.**
- Weighed against miniflare/`wrangler dev`: workerd would give real DO semantics and D1, but means a wrangler dependency (and its download) for `dev`, a bundle per save, and a restart of the DO namespace on each reload; the runtime would be tested twice anyway. Parity is already proven where it matters: the kernel's drivers through `parity.ts` (memory under bun, DOs in workerd), the runtime through its workerd tests (`runtime/test`) on the same code. Dev starts in tens of milliseconds, and an in-process swap keeps state for free. ponytail: no workerd limits in dev (CPU time, subrequests) and the index is memory rather than D1; `openconnect dev --remote`/`--workerd` on top of #31's Worker entry if a user hits a difference.
- **Real clock, in the driver** (`memory(program, { clock: Date.now })`): `now()` follows the clock and one wall-clock timeout fires the earliest timer of any instance; `advance(ms)` still works on top as a skew (tests drive retries with it). Timers keep the existing semantics (removed before firing, earliest first, one run at a time, a throwing one logged, synchronous throws included, in both modes); timeouts are unref'd, and `stop()` stops firing (they stay stored). A ticker outside the driver calling `advance` was the alternative: no driver change, but the clock would be frozen while a slow timer ran (a 10 s event POST), which skews TTLs and token expiry.
- **Persistence: a snapshot, not a database.** `dump()` returns every instance's store, version counter and timers as JSON; `memory(p, { snapshot })` restores them (instances eagerly, so their timers are found before a first call). Dev writes `.openconnect/state.json` when it changed (polled every 500 ms, atomic rename, mode 0600 like `dev.vars`: handshakes and outboxes aren't sealed) and on exit; the watcher ignores it. `stop()` is idempotent. ponytail: a hard kill loses up to half a second of writes; hook the store's writes if that bites. The index isn't saved: on start, every restored connection gets `index.sync` (#26's repair path), which also runs each extension's first `after()`, as in a fresh isolate. `--reset` starts empty.
- Parity: `World.restart?()` is new in `parity.ts`, with a test that state, versions (no ABA across the restart), TTLs and timers survive one; memory runs it, the DO world doesn't provide it (its storage is durable by construction). Memory also runs the whole suite in clock mode (a clock that doesn't move, so `advance` is the skew). Timers firing on their own is memory-only in `memory.test.ts`: it's what the DO's real alarms do, which the DO parity run keeps off on purpose (#14).
- One process: the Worker's `fetch` and every instance share it, with `api.now` = the driver's clock. Bound to `localhost`. Each request is logged as method, path (no query: it carries codes and states), status and time.

**Hot reload.** The config is bundled with `Bun.build` (`packages: "external"`) into `.openconnect/build/config-<n>.js` and imported, so every reload sees fresh code for the config and every local file it imports, while packages stay one copy (so `instanceof` on kernel errors still holds). A query-string cache-buster wouldn't do: it re-runs only the entry, not its imports. A recursive `fs.watch` on the project directory (not `node_modules`, `.openconnect`, `.git`), debounced 50 ms, reloads on any save, `.dev.vars` included (settings are rebuilt with the definitions).
- The swap: the driver's handler for each instance delegates to the current runtime's `program`, and re-creates its inner handler after a reload. That's what a deploy does to isolates: per-isolate memory (single-flight, the index/events/webhooks "last seen" marks) goes, the store stays, and every extension already handles a fresh isolate. An in-flight call finishes on the code it started with. An instance moves to the new code only when idle (no call or timer running on it); until then new calls join the old handler, so one instance never has two live handlers, which a DO never allows and the events outbox relies on (`swappable()` in `dev.ts`). ponytail: an instance that's never idle keeps the old code.
- A load is built, imported, resolved and its settings imported before anything is swapped; any error is printed and the previous version keeps serving. A config that fails on the first load serves 503 `not_ready` until a save fixes it. A definition removed from the config leaves its connections stored (they answer 404 until it comes back). ponytail: files outside the project directory aren't watched; and nothing checks that a changed definition can still read the metadata it wrote (#17's rule stands).

**OAuth callbacks.** The banner prints the exact redirect URI to register (`<public URL>/callback`) and the webhook URLs. GitHub and Google take `http://localhost`; Slack wants https, so:
- `--tunnel` spawns `cloudflared tunnel --no-autoupdate --url http://localhost:<port>` (a quick tunnel: no account, a new `https://*.trycloudflare.com` each run), parses the URL from its log and uses it as the public URL. Not installed → an explanation with install links and the `--url` alternative, exit 1 (it was asked for explicitly). No dependency: it's a process we spawn if it's there.
- `--url https://…` for a tunnel the user runs (ngrok, a named cloudflared tunnel with a stable hostname, which Slack's fixed redirect URL prefers), and `OPENCONNECT_PUBLIC_URL` in `.dev.vars` works too. Precedence: `--url`, `--tunnel`, the env, `http://localhost:<port>`.
- From #29: the connect UI's `url` must be the same origin as `/callback`, so with a tunnel the app's pages use the tunnel URL; `Secure` cookies work on both https and `localhost`. Session `origins` are the app's own (often `http://localhost:3000`).

**Commands.** `src/args.ts` is a 30-line parser: `command`, declared flags only (`--flag v`, `--flag=v`, switches), so a typo is an error, not ignored. No dependency. `openconnect dev [--port 8787] [--config file] [--tunnel] [--url url] [--reset]`, `openconnect help|--help|-h`. `deploy` is a stub naming #31. `main(argv)` resolves to an exit code or a running server's `stop` (the bin calls it on SIGINT/SIGTERM: final snapshot, tunnel killed). ponytail: Bun only (`#!/usr/bin/env bun`): the config is TypeScript and the reload uses `Bun.build`; a Node build of the bin comes with publishing.

**Example:** `examples/basic` (a workspace, so its `openconnect` bin links to the package): GitHub, Slack and Google from `@openconnect/providers` configured from `.dev.vars` when set, and one local API-key definition (`notes.ts`) to edit while it runs. The root `tsc` checks `examples/*`.

**For #31 `deploy`:** reuse `options(config, env, d1Index("INDEX"))` inside a generated Worker entry (`import config from "<project>/openconnect.config.ts"`, `env` from `cloudflare:workers`, then `cloudflare(runtime(opts), { binding })`), `generateKeys()` + `ENV` for `wrangler secret put`, `.dev.vars` for the user's provider secrets, and `OPENCONNECT_PUBLIC_URL` = the workers.dev URL or custom domain. `project.ts` needs a Workers-types typecheck pass once it is bundled into a Worker.

Tests (`packages/cli/src/*.test.ts`, bun): dotenv parsing and the flag parser; keys generated once, gitignored, kept across runs, the project's env winning; config as a function of `.dev.vars` and the process env, the banner, unconfigured definitions, `OPENCONNECT_PUBLIC_URL` in the redirect URI; a missing config, duplicate ids and a broken first load (503, then fixed by a reload); the dev server on a free port driven by the SDK against local servers: oauth2 connect through `/callback`, API-key connect, list, proxy with header and query injection, lifecycle events delivered by the real-clock timers and verified by the SDK's `handle`; hot reload through the watcher (a changed import: the old connection stays active and its token unseals, a new one runs the new code) and a broken save keeping the old version; a restart keeping connections, tokens and the rebuilt index, and `--reset`; tunnel URL parsing, a fake `cloudflared` script, a missing one; the CLI's help, flag errors and the deploy stub; and `examples/basic` loading. Kernel: the restart parity test, the suite in clock mode, timers firing on their own across a restart, `stop()`.

## #31 CLI `openconnect deploy` — decided

`openconnect deploy` puts the project into the user's own Cloudflare account: `src/generate.ts` writes the Worker, `src/deploy.ts` drives wrangler. Same `openconnect.config.ts` as `dev` (#30); one new optional field, `deploy: { name?, url? }`.

```
openconnect deploy --env-file .prod.vars [--name n] [--url https://connect.example.com] [--rotate key,api-key,state,sessions] [--new-keys] [--dry-run]
```

**Wrangler under the hood, spawned, not the Cloudflare API.** Wrangler already does what a deploy needs and we'd otherwise rebuild: login (OAuth or `CLOUDFLARE_API_TOKEN`) and account selection, esbuild bundling with the Workers conditions, DO class migrations, D1 create and migrations, versioned secret uploads. Calling the API directly would mean the multipart script upload, metadata for bindings and migrations, and our own auth flow, for no gain in a self-host path whose users already use Cloudflare. It isn't a dependency of the CLI: the user installs it (`bun add -d wrangler`), as with cloudflared in #30. The binary is `OPENCONNECT_WRANGLER`, else the project's `node_modules/.bin/wrangler`, else `wrangler` on PATH; missing → install and login instructions. Spawned with stdin closed (non-interactive, so `migrations apply` doesn't prompt), output echoed except listings; a non-zero exit stops the deploy with wrangler's output.

**Generated files: `.openconnect/deploy/`** (gitignored by `.openconnect/.gitignore`, rebuilt on every deploy, nothing secret in them):
- `worker.ts`: a copy of the template `packages/cli/src/worker.ts` with its imports pointed at resolved paths: the user's config (relative), this CLI's `project.ts`, and `@openconnect/runtime` (+ `/cloudflare`) as the user's project resolves it (the CLI's copy as a fallback). The CLI takes `@openconnect/runtime`, `kernel` and `connections` as **peer dependencies**, so an installed project has one copy of each, shared by its definitions and the runtime; two bundled copies would break `instanceof` on kernel errors. It's `cloudflare(runtime(options(config, env, d1Index("INDEX"))), { binding: "CONNECTION" })` with `export class Connection` and `export default { fetch }`. `options` runs at module scope against `env` from `cloudflare:workers` (definitions are needed up front); keys still load lazily on the first request. The template is a real file typechecked with Workers types (`packages/cli/tsconfig.workers.json`, also covering `project.ts`), so it can't drift from the runtime's API; `src/config.d.ts` types its `openconnect:config` import.
- `wrangler.json`: name, `main`, `compatibility_date` (pinned in the CLI, `2026-09-01`, as in the tests; ponytail: no per-project compatibility flags yet), DO binding `CONNECTION` → `Connection` with migration `v1` `new_sqlite_classes` (SQLite storage, #13), D1 binding `INDEX` (`<name>-index`, its id, `migrations_dir: "migrations"`), `vars.OPENCONNECT_PUBLIC_URL`, and `workers_dev`, or a custom-domain route.
- `migrations/`: the runtime's `migrations/*.sql` (#26) copied next to the config, found from the resolved runtime package. The runtime's `package.json` lists `files: ["src", "migrations"]` so a published package ships them.
- `state.json`: `{ name, url, databaseId }`, not secret: the workers.dev URL and the D1 id, so re-deploys need one `wrangler deploy`.

**Steps** (each idempotent):
1. `wrangler secret list --name <n> --format json`: what the Worker already has. Only Cloudflare's "no such Worker" (`[code: 10007]` / "does not exist on your account") means a new Worker; any other failure stops, so a misread listing can never put fresh keys over live ones.
   - An existing Worker whose public URL isn't known here (no `--url`, no `deploy.url`, no `state.json`: a fresh checkout in CI) is refused, naming the flag. Deploying it without the var would make wrangler drop the live `OPENCONNECT_PUBLIC_URL` (vars are replaced on deploy) and every request would 500. Wrangler can't tell us the account's workers.dev subdomain before a deploy (no `subdomain` command in 4.x, `whoami` doesn't show it), and `keep_vars` would keep the var but not a custom-domain route, so asking is the safe choice. CI sets `deploy.url` once.
2. `wrangler d1 list --json`, `d1 create <n>-index` if it isn't there (then listed again for its id). Found by name, so a deploy from another machine finds the same database. **An index database without its Worker** (the Worker was deleted, or an earlier deploy stopped before creating it) is refused unless `--new-keys`: fresh keys can't open anything sealed before, so starting over is said out loud.
3. `wrangler d1 migrations apply <n>-index --remote --config …`: applies only what's new.
4. `wrangler deploy --config … --secrets-file <tmp>` when any secret is due: wrangler 4.x uploads them **with the version** (additive: omitted ones stay), so new code never runs without its new secret and a new Worker never runs without keys. The file is `secrets.json`, mode 0600, in a fresh `mkdtemp` directory, removed in `finally`, and by one-shot SIGINT/SIGTERM handlers around that step (a signal skips `finally`), which also kill wrangler and exit 130/143; secrets never go in argv. Chosen over `secret bulk` on stdin (the first version): stdin kept them off disk, but `bulk` is a separate step that runs before or after the version, never with it. A deploy that fails after generating an API key says so: if it went through anyway, `--rotate api-key` makes one that can be shown.
5. A new Worker with no URL given: the workers.dev URL is read from wrangler's output and the Worker is deployed again with it as `OPENCONNECT_PUBLIC_URL` (no secrets: they're already there). ponytail: until that second deploy (seconds) the new Worker answers 500, which no one is using yet; `state.json` remembers the URL.
**Public URL.** `--url` (or `deploy.url`): https, an origin served at its root (the runtime routes by first path segment, so `/oc` prefixes are refused); a non-workers.dev host also gets `routes: [{ pattern, custom_domain: true }]` and `workers_dev: false`. Otherwise the workers.dev URL. It's a var, not a secret: callback and webhook URLs are public. The summary prints the callback URL to register with each provider and the webhook URLs.

**Secrets UX.**
- **Runtime keys** (`OPENCONNECT_KEY_V1`, `STATE_KEY`, `SESSIONS_KEY`, `WEBHOOKS_KEY`) are generated by `generateKeys()` on the deploy that finds them missing, pushed, and never shown, stored or read from any file. Dev keys are never reused: they're never read, an env file containing a runtime key is refused, `--env-file .openconnect/dev.vars` is refused, and a value equal to the dev one in `.openconnect/dev.vars` is refused.
- **Provider secrets** (client ids/secrets, signing secrets) come from the env file the user names (`--env-file .prod.vars`, dotenv syntax, `.prod.vars` added to the root `.gitignore`) and are pushed on every deploy that names it (secrets are write-only, so there's nothing to diff against; `bulk` upserts). Everything in the file becomes a secret, so the config's `env.X` reads them in the Worker exactly as `.dev.vars` in dev. `OPENCONNECT_PUBLIC_URL` in it is refused (it's `--url`'s).
- **API key:** the env file's `OPENCONNECT_API_KEY` if set (never printed), else generated on the first deploy and printed once, after the deploy succeeded, with a note that it can't be read back. The only secret ever printed.
- **Events secret:** the user's app needs it too, so it's the user's: `OPENCONNECT_EVENTS_SECRET` in the env file. With `events` in the config and the secret neither in the file nor on the Worker, deploy stops before changing anything, saying how to make one (`whsec_` + 32 random bytes in base64), rather than generating and printing it.
- **Rotation, explicit only:** `--rotate key` adds `OPENCONNECT_KEY_V<max+1>`; the old versions stay, so everything sealed under them still opens and is re-sealed on read (#10). ponytail: retiring an old version needs to know nothing is sealed under it any more; not automated. `api-key` (prints the new one; the app must switch), `state` (in-flight handshakes, 10 min, fail), `sessions` (issued session tokens, ≤1 h, fail). `webhooks` is refused: it would break every registered hook (#25's ponytail, no key versions); `events` is refused (change it in the env file and the app). A rotation of a key the env file supplies is refused.

**`--dry-run`** writes `.openconnect/deploy/` (with the remembered D1 id, or a placeholder) and prints the plan: name, public URL, definitions and the ones missing config, how many secrets from which file, rotations, steps. No wrangler call. `wrangler deploy --dry-run -c .openconnect/deploy/wrangler.json` then bundles it offline (checked by hand on `examples/basic`: 89 KiB, both bindings listed).

**Managed: deferred to #34.** `--managed` answers that it waits for the managed service. What the CLI would upload (one Bun.build bundle of the definitions with `@openconnect/*` external? per-app connector config instead of Worker secrets?) depends on how #34 isolates user code and stores per-app config; a contract written now would be a guess. ## #32 Dashboard — decided

`packages/dashboard` (`@openconnect/dashboard`): `dashboard()`, an Extension that serves a small UI at `/dashboard` from the runtime's own Worker, so every self-host deployment has it with nothing else to deploy, plus a few runtime methods it needs (`events.status`, `events.flush`, `events.redeliver`, `webhooks.status`). On by default in `openconnect dev` and `deploy` (`dashboard: false` in the config leaves it out); the dev banner and the deploy summary print its URL.

**OSS vs managed.** The self-host dashboard is one deployment's operator console, for whoever holds its API key: list, search and filter connections; one connection's state, reason, metadata, external ids, events outbox and webhook registration; actions (revoke, `index.sync`, deliver now, redeliver, connect or re-authorize); the definitions and the URLs to register with each provider. Managed-only, in `openconnect-cloud` (#3): accounts and sign-in (Clerk), orgs and multiple apps per tenant, team members and roles, per-user audit log, billing and usage metering, connector config entered in a UI (self-host config is code + env, #30), user-code upload and isolation (#34), cross-tenant views. Those need a user model the OSS runtime doesn't have (one deployment = one app, one API key, #22). Managed can mount this one's routes inside its own shell, or not; nothing here assumes a tenant.

**v1 `apps/dashboard` (deleted in 2dcdb10): not reused.** It was a React + TanStack Router + Vite SPA behind Clerk, calling a `/management/*` API that no longer exists (connectors, API keys, connections by `do_name`/`tenant_id`). Clerk is managed's concern; the API it spoke is gone; and React + Vite would bring a toolchain into a repo whose browser code is zero-dependency (#29) for a few tables and forms. Kept from it: the shape, a static client-only UI served same-origin by the Worker (no CORS, one deployment).

**Serving: a runtime Extension, assets committed.**
- `GET /dashboard` the page, `/dashboard/app.js`, `/dashboard/app.css` (public: nothing secret in them), `GET /dashboard/api/overview` and `GET /dashboard/api/connections/:def/:id` (API key, checked in the route with the runtime's `authorized`, now exported from `http.ts`). Lists and actions go to the runtime's own routes (`GET /connections?…`, `POST /connections/:def/:id/<method>`): the dashboard is an API client, so it can't do anything the API key can't.
- The UI is TypeScript in `src/app.ts` (DOM only, no dependency, `tsconfig.web.json` checks it with no Bun/Node types), bundled by `bun run build` (`build.ts`, `Bun.build`, minified, ~14 KB) into `src/assets.ts` as string constants, committed. So the runtime, the Worker bundle (wrangler's esbuild), workerd tests and dev need no build step or text-import rules, which differ in each of them. The file carries a SHA-256 of its sources as `version`; a test fails when it's stale (comparing source hashes, not bundler output, so a Bun upgrade doesn't break it). `version` is also the cache-buster: `?v=<version>` URLs are `immutable`, anything else `no-cache`; the page is `no-store`.
- `Function.prototype.toString` of a bundled function was the zero-file alternative; rejected: wrangler bundles with `keep_names`, which injects `__name()` calls that don't exist in the browser.
- Its own package, not `runtime/src`: browser code, a build script and DOM tests stay out of L3; it uses only the runtime's public API (L4 on L3). The runtime is a peer dependency (`Fail` must be the runtime's own for `instanceof`); the CLI depends on it.

**Auth: the API key, held by the tab, sent as a Bearer header.** A login form checks the key against `/dashboard/api/overview` and keeps it in `sessionStorage` (this tab only, survives a reload, gone when the tab closes); every fetch is same-origin with `Authorization: Bearer`. A 401 `unauthorized` (the key was rotated) clears it and shows the login again. Weighed against an HttpOnly cookie from `POST /dashboard/login`:
- Bearer from script: no cookie means no CSRF at all (a cross-site page can't make the browser attach the header), and no second credential on the admin API: the server side is unchanged, every route already takes Bearer. The cost is that script on the dashboard's origin can read the key, so the page is locked down: CSP `default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`, no inline script or style at all (so no nonce needed), `nosniff`, `no-referrer`, COOP `same-origin`; the UI builds every node with `createElement` and text (a test greps `app.ts` for `innerHTML`/`insertAdjacentHTML`/`document.write`/`eval`), and links from API data are http(s) only. The origin's other pages are the runtime's own (`/callback`'s popup page with its own nonce CSP, JSON elsewhere).
- Cookie: the key never reaches script, but every admin route would have to accept the cookie, which makes the whole API (revoke, token, proxy) a CSRF target that needs SameSite + Origin checks + a CSRF token on each of them, plus a signing key, expiry and logout for sessions. An XSS could still drive the API through the cookie; what it gains is not exfiltrating a key that works until rotated.
- Chosen: Bearer, for no new server-side auth surface. ponytail: whoever signs in holds the deployment's full API key; a scoped, read-only or expiring dashboard credential (a signed short-lived token, as sessions do in #29) when a team shares a self-host dashboard. Managed has users and roles instead. No rate limit on the login check (API keys are 32 random bytes).

**What it shows, never secrets.** No credential or token (the UI never calls `token`), no connector config values (`overview` lists config *names* that are empty: `missing: ["clientId"]`, and `configured` = has an entry, which is what `not_configured` checks), no keys, no webhook secret (`webhooks.status` gives the ingress URL only), no events secret, and the events URL with its query replaced by `?…` (it may carry a token). Metadata is shown: it's what `GET /connections/:def/:id` already returns, by definition who the account is. Webhook payloads aren't listed (topic and delivery id only); a registration's `hook` is, and `Webhooks.register`'s doc now says it holds ids, not secrets (it was already stored unsealed).

**Views** (hash routes, rendered by one `render()`; a newer render wins over a slower one):
- **Connections** (`#/?def=&state=&q=`): the index (#26) with its filters and search (id or any external id), keyset "Load more" in place; without an index it says so and still offers "open by definition + id".
- **Connection** (`#/c/<def>/<id>`, one `GET /dashboard/api/connections/:def/:id`: `status`, `events.status`, `webhooks.status` in parallel, external ids computed in the Worker from the metadata with the definition's `external`). Each part is the runtime's `Reply` as is, so a missing extension shows as such. Actions: revoke (`confirm()` first; reason `dashboard`), sync index, refresh, deliver now, redeliver per recent event, and connect / re-authorize: API-key fields go to `connect` (password inputs for secret-looking names, as in #29); an OAuth definition gets the provider URL as a link in a new tab (`noopener noreferrer`), finishing at `/callback` as JSON. That URL isn't bound to a browser (#28's login-CSRF caveat); it's an operator connecting a test account in their own browser. ponytail: a session-based connect (#29) would need the dashboard's origin in `sessions.origins`; add it if operators connect real users' accounts from here. Looking at a connection that doesn't exist creates nothing (no write on any path).
- **Definitions** (`#/definitions`): the callback URL to register, webhook base, events URL, session origins, index on/off; per definition its flow (redirect or form + fields), config state, proxy base URL, and its webhook ingress URLs (app-level `/webhooks/:def`, per connection `/webhooks/:def/:id`, and whether it registers them itself).

**Runtime additions (events, #24's deferred replay).**
- **`events.status`** (public method, API key): `{ enabled, pending, attempt, retryAt, error, queued, recent }`. `error` is new on the head: why the head's last attempt failed (`HTTP 503`, `timeout`, `network error: …`; no URL, header or body), written in the failure's cas, cleared by the 2xx's. `queued` = the first 20 pending, head first; `recent` = the newest done ones. Each as `EventSummary { slot, id, seq, type, at, data }`, `data` without webhook payloads.
- **`events.flush`**: "deliver now". Clears a parked `retryAt` (keeping `attempt`, so a failure continues the backoff where it was) and arms `events.retry` now. The POST still happens in the timer, not in the method: timers don't overlap per instance, so the outbox keeps one delivery in flight and its order; a method that POSTed itself could run alongside a drain and send a later event before an earlier one's retry. Returns the status after arming; the page says to refresh.
- **`events.redeliver({ slot })`** (replay): copies a done event to the back of the outbox, **the same body and `webhook-id`** (the copy keeps the original `id`, `seq`, `at`; only its slot is new). That is exactly an at-least-once duplicate, which receivers already handle: one that dedupes on `webhook-id` skips it, so to reprocess, the receiver drops that id first (Svix replays the same way). A new id was the alternative, but then a receiver can't tell a replay from a new event. It goes behind what's queued, so the outbox order is kept. Refused: `pending` (409) for an event not delivered yet, `not_found` past the kept window, `not_configured` without `settings.events`.
- **Retention:** done events (delivered, or dropped past the 1000 cap) are no longer deleted at once; the newest `KEPT = 20` stay (`events.e:<seq>` for seq in `(done - 20, done]`), and each move of `done` frees what fell out (`retire`). Up to 20 extra values per connection; with webhook payloads up to 1 MB each (#25) that's ≤ 20 MB in a DO's storage, worst case. ponytail: count, not bytes; no replay of a range (one event per call) and no replay past 20; a dropped event within the window isn't marked as dropped (it shows as done, and redelivering it delivers it for the first time). Tests that counted zero live keys after delivery now count `KEPT`.
- **`webhooks.status`**: `{ supported, registers, url, registration: { hook, renewAt, account } | null, pending }`. Not the secret.
- ponytail: no "register webhooks now" action (the registration timer retries on its own and re-arms on the next state change, #25); no dead-letter view beyond the parked head; no bulk actions.
